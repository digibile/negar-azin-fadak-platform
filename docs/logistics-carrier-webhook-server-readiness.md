# ممیزی آمادگی Backend برای دریافت webhook شرکت حمل

تاریخ: ۲۰۲۶-۱۱-۲۲  
شاخه بررسی‌شده: `feat/commerce-management-workspace`  
وضعیت: ممیزی فقط‌خواندنی؛ بدون تغییر API، middleware، migration یا تنظیمات عملیاتی.

## ۱. شواهد موجود در کد

فایل مرجع: `apps/api/src/server.ts`

1. بدنه JSON با `express.json({ limit: "12mb", verify: ... })` parse می‌شود.
2. در callback مربوط به `verify`، بایت‌های بدنه در `req.rawBody` به‌صورت Buffer کپی می‌شوند. بنابراین ماده خام برای اعتبارسنجی امضای مبتنی بر raw body در middleware فعلی در دسترس است.
3. middleware ضد CSRF برای درخواست‌های تغییردهنده به‌صورت پیش‌فرض اجرا می‌شود.
4. استثنای عمومی webhook فعلی فقط برای مسیر زیر است:
   `POST /api/payment-gateways/:provider/webhook`
5. هیچ استثنای CSRF برای مسیر شرکت حمل در middleware فعلی تعریف نشده است.
6. `logisticsRouter` در سرور mount شده و مسیرهای دامنه لجستیک از همان router موجود سرو می‌شوند.
7. فایل `apps/api/src/payment-provider.ts` قرارداد و adapter پرداخت را تعریف می‌کند؛ این قرارداد برای شرکت حمل قابل استفاده مجدد فرض نمی‌شود، چون چرخه، رویدادها و شواهد تحویل متفاوت‌اند.

## ۲. نتیجه فنی

زیرساخت فعلی برای نگهداری raw body یک نقطه شروع مناسب دارد، اما به‌تنهایی به معنی آماده بودن webhook شرکت حمل نیست.

پیش از انتشار endpoint شرکت حمل، باید موارد زیر به‌صورت محدود و قابل آزمون پیاده شوند:

- مسیر webhook مستقل و صریح، بدون احراز هویت کاربر، اما با احراز اصالت پیام بر اساس مستند رسمی ارائه‌دهنده.
- استثنای CSRF فقط برای همان الگوی مسیر webhook؛ نه حذف یا تضعیف CSRF به‌صورت عمومی.
- بررسی امضا روی `req.rawBody`، با مقایسه constant-time و کنترل timestamp/replay مطابق قرارداد ارائه‌دهنده.
- نگاشت provider به پیکربندی فعال و secret همان provider از سمت سرور؛ نام provider یا tenant ارسالی در payload قابل اعتماد نیست.
- محدودیت اندازه بدنه متناسب با webhook، محدودیت نرخ، timeout و پاسخ خطای کنترل‌شده.
- ثبت durable و idempotent شناسه رویداد قبل از اعمال اثر دامنه‌ای؛ رویداد تکراری نباید وضعیت مرسوله یا موجودی را دوباره تغییر دهد.
- پردازش transition از همان قواعد مجاز لجستیک و ثبت audit؛ webhook نباید مستقیماً SQL تغییر موجودی یا وضعیت دلخواه اجرا کند.
- حفاظت از داده‌های گیرنده و حذف payload حساس از logهای عمومی.

## ۳. ترتیب پیاده‌سازی پس از انتخاب شرکت حمل

1. دریافت مستند رسمی امضا، timestamp، event ID، retry و payload نمونه sandbox.
2. تصویب مسیر و روش احراز اصالت با توجه به همان مستند.
3. افزودن تست‌های واحد برای امضای معتبر/نامعتبر، timestamp منقضی، replay و event ID تکراری.
4. افزودن inbox پایدار با قید یکتای provider/event ID و tenant-safe linkage؛ طراحی migration باید پس از شناخت مدل worker و سیاست نگهداری داده انجام شود.
5. پردازش inbox از طریق worker موجود پروژه، نه ساخت صف موازی.
6. اعمال نگاشت وضعیت فقط با transition مجاز و بدون آزادسازی/افزایش خودکار موجودی بر اساس webhook.
7. اجرای sandbox end-to-end و بررسی audit/reconciliation.
8. فعال‌سازی production فقط پس از تأیید انسانی و ثبت secret در سامانه امن پیکربندی.

## ۴. مواردی که هنوز اثبات نشده‌اند

- وجود یا نبود worker مناسب برای پردازش durable inbox در تمام مسیرهای پروژه در این ممیزی بررسی نشده است.
- سازوکار rate limiting عمومی و سیاست نگهداری payload در کل سرویس در این ممیزی بررسی نشده است.
- هیچ شرکت حمل، الگوریتم امضا، header، event ID یا schema مشخصی انتخاب نشده است.
- هیچ endpoint عمومی webhook حمل در این تغییر ساخته یا فعال نشده است.

## ۵. محدودیت ایمنی

تا دریافت قرارداد رسمی provider، نباید header امضا، الگوریتم HMAC، timestamp tolerance، شناسه event، payload یا وضعیت‌های حمل حدس زده شوند. هیچ webhook واقعی، ارسال مرسوله، تغییر وضعیت مرسوله یا عملیات موجودی در این مرحله انجام نشده است.
