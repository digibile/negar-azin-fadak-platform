# طراحی پردازش رویدادهای شرکت حمل با استفاده از Worker موجود

تاریخ: ۲۰۲۶-۱۱-۲۲
مخزن: `digibile/negar-azin-fadak-platform`
شاخه: `feat/commerce-management-workspace`
مبنای بررسی: کد موجود در همین شاخه؛ این سند طراحی است و به‌تنهایی به معنی پیاده‌سازی یا فعال بودن اتصال حمل نیست.

## ۱. یافته‌های قطعی از کد

### Worker موجود
فایل `apps/api/src/notification-worker.ts` یک پردازشگر دائمی با چرخه راه‌اندازی و خاموشی کنترل‌شده دارد. در هر چرخه:
- `sweepPaymentReviews` بررسی پرداخت‌های پذیرنده را انجام می‌دهد.
- `scheduleCommerceReminders` یادآوری‌های موعدرسیده خرید را به اعلان تبدیل می‌کند.
- `claimBatch` ردیف‌های `notification_outbox` را با `FOR UPDATE SKIP LOCKED` برمی‌دارد و به وضعیت `processing` می‌برد.
- قفل با `locked_at` و `locked_by` ثبت می‌شود و پردازش‌های منقضی‌شده دوباره به صف برمی‌گردند.
- خطاها با شمارنده تلاش و `available_at` زمان‌بندی مجدد می‌شوند و پس از سقف تلاش به `failed` می‌رسند.
- خاموشی با سیگنال‌های `SIGTERM` و `SIGINT` کنترل می‌شود.

این Worker در وضعیت فعلی، Worker عمومی رویداد نیست. تابع `deliver` فقط کانال اعلان را پردازش می‌کند و برای کانال‌های فاقد provider خطا می‌دهد.

### موتور رویدادهای کسب‌وکار
فایل `apps/api/src/business-events.ts` تابع `emitBusinessEvent` را دارد. این تابع قواعد فعال tenant را از `rule_definitions` می‌خواند، اجرای قواعد را در `rule_executions` ثبت می‌کند و برای actionهای اعلان، ردیف‌های `platform_notifications` و `notification_outbox` می‌سازد.

این مسیر اجرای قواعد و اعلان است؛ قرارداد durable inbox برای دریافت callback بیرونی شرکت حمل در آن مشاهده نشد.

### مرز فعلی webhook
در `server.ts` بدنه خام درخواست برای بررسی امضا نگهداری می‌شود. استثنای CSRF فعلی فقط مسیر webhook درگاه پرداخت را پوشش می‌دهد. تست `logistics-carrier-webhook-readiness.test.ts` نیز نبود webhook عمومی شرکت حمل و مستقل بودن قرارداد پرداخت از حمل را صریحاً کنترل می‌کند.

## ۲. تصمیم معماری پیشنهادی

1. از همان فرایند و چرخه عمر `notification-worker` برای اجرای پردازش رویدادهای حمل استفاده شود؛ سرویس یا فرایند Worker موازی ساخته نشود.
2. رویداد ورودی حمل در جدول inbox مستقل و پایدار نگهداری شود. استفاده از `notification_outbox` برای payload حمل رد می‌شود، چون جدول فعلی برای تحویل اعلان و وضعیت ارسال آن طراحی شده است.
3. مصرف inbox با تابع claim اختصاصی و قفل ردیفی `SKIP LOCKED` انجام شود. الگوی lease، مالک قفل، شمارنده تلاش، زمان تلاش بعدی و بازیابی پردازش منقضی‌شده می‌تواند با الگوی Worker موجود هم‌راستا باشد؛ اما منطق اعلان و منطق رویداد حمل در یک handler ادغام نشوند.
4. شناسه یکتای رویداد در محدوده ارائه‌دهنده و حساب/اتصال معتبر حمل باید پیش از هر اثر دامنه‌ای ثبت و با قید یکتا محافظت شود. تکرار callback باید پاسخ idempotent داشته باشد و transition یا اثر موجودی را دوباره اجرا نکند.
5. اعمال رویداد فقط از مسیر قواعد transition موجود لجستیک انجام شود. handler مجاز به اجرای SQL دلخواه برای تغییر وضعیت، رزرو، مصرف یا بازگرداندن موجودی نیست.
6. رویداد ناشناخته، نامعتبر یا غیرقابل اعمال باید قابل ممیزی و تعیین تکلیف باشد؛ نباید با تبدیل خاموش آن به موفقیت حذف شود.
7. payload خام و داده‌های شخصی گیرنده در log عمومی ثبت نشوند. حداقل داده لازم، شناسه رویداد، provider، نتیجه اعتبارسنجی و ارجاع داخلی نگهداری شود.

## ۳. جریان هدف پس از انتخاب شرکت حمل

1. endpoint اختصاصی، بدنه خام را دریافت می‌کند و اصالت پیام را دقیقاً مطابق مستند رسمی همان ارائه‌دهنده بررسی می‌کند.
2. پس از اعتبارسنجی provider/account و ساختار پیام، رویداد در inbox با کلید idempotency ثبت می‌شود.
3. اگر رویداد تکراری باشد، از ایجاد اثر دامنه‌ای مجدد جلوگیری می‌شود.
4. Worker موجود، inbox را با claim مستقل برمی‌دارد و handler حمل را اجرا می‌کند.
5. handler ارتباط رویداد با tenant، سفارش، درخواست تأمین و مرسوله را از داده‌های داخلی و معتبر پیدا می‌کند.
6. transition مجاز لجستیک در تراکنش کنترل‌شده اجرا و audit ثبت می‌شود.
7. نتیجه پردازش، زمان، تعداد تلاش و خطای کنترل‌شده ثبت می‌شود؛ رویدادهای نیازمند بررسی انسانی در وضعیت قابل مشاهده باقی می‌مانند.

## ۴. مواردی که پیش از migration و endpoint باید مشخص شوند

- شرکت حمل و مستند رسمی webhook آن.
- روش امضا، نام headerها، الگوریتم، قالب timestamp و بازه مجاز زمانی.
- شناسه یکتای event و قواعد retry ارائه‌دهنده.
- schema واقعی payload و نسخه‌بندی آن.
- روش تشخیص حساب/اتصال حمل و نگاشت آن به tenant؛ tenant ارسالی در payload به‌تنهایی قابل اعتماد نیست.
- ماتریس نگاشت eventهای provider به transitionهای مجاز موجود.
- سیاست نگهداری payload، داده شخصی و رویدادهای dead-letter/نیازمند بررسی.
- رفتار پاسخ HTTP برای رویداد تکراری، نامعتبر و خطای موقت.

تا تعیین این موارد، نام جدول نهایی، ستون‌های provider-specific، header امضا، payload، endpoint عمومی و migration اجرایی تصویب نمی‌شوند.

## ۵. ترتیب اجرای مرحله بعد

1. انتخاب provider و دریافت مستند رسمی و نمونه‌های sandbox.
2. استخراج ماتریس event به transition از مستند provider و state machine موجود لجستیک.
3. طراحی و بازبینی schema inbox مستقل با tenant-safe foreign key و unique key واقعی provider/event.
4. پیاده‌سازی تست‌های اعتبارسنجی امضا، timestamp، replay، duplicate، tenant isolation و transition غیرمجاز.
5. افزودن consumer مستقل inbox به چرخه Worker موجود، بدون افزودن فرایند یا صف موازی.
6. آزمون PostgreSQL هم‌زمانی، crash recovery، retry و idempotency.
7. آزمون end-to-end در sandbox ارائه‌دهنده و سپس بازبینی انسانی پیش از فعال‌سازی عملیاتی.

## ۶. محدوده این تغییر

این سند فقط تحلیل و طراحی مبتنی بر کد فعلی است. هیچ migration، endpoint، webhook عمومی، تغییر موجودی، ارسال مرسوله، تغییر وضعیت عملیاتی، تنظیم secret یا استقرار Production در این مرحله انجام نشده است.
