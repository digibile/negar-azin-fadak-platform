# تصمیم معماری: مرجع واحد طرف‌حساب و حساب‌های بانکی ذی‌نفعان

تاریخ: ۲۰۲۶-۱۰-۳۰  
وضعیت: پیاده‌سازی اولیه در PR #124؛ منتظر CI نهایی و بازبینی؛ بدون اعمال روی دیتابیس زنده  
مخزن: `digibile/negar-azin-fadak-platform`

## مسئله

ممیزی VamCity نشان داد `CounterParty` فقط نام، شبا و وضعیت فعال دارد. مقصد هم برخلاف برداشت اولیه، دفتر عمومی طرف‌حساب را از قبل دارد؛ اما چند زیرسیستم رجیستری‌های تخصصی جداگانه ساخته‌اند و حساب بانکی بیرونی به مرجع عمومی party متصل نیست.

اصل معماری کتاب `docs/architecture/BOOK-2026.md` الزام می‌کند هر تغییر در محل canonical انجام شود و قبل از ایجاد endpoint/table جدید، مسئولیت‌های مشابه جست‌وجو شوند.

## وضعیت فعلی مقصد که با کد/DDL اثبات شده است

| موجودیت | مسئولیت فعلی | محدودیت برای مرجع واحد |
|---|---|---|
| `accounting_parties` (migration 089) | اشخاص/شرکت‌ها با نوع customer/supplier/employee/agent/bank/other، کد، شناسه‌های ملی/مالیاتی، تماس، نشانی، حساب پیش‌فرض، اعتبار و مهلت پرداخت | مرجع عمومی موجود؛ فاقد IBAN و رابطه حساب بانکی بیرونی |
| `accounting_bank_accounts` (migration 089) | حساب بانکی ثبت‌شده در خزانه/حسابداری tenant، با کد، بانک، شماره حساب، شبا، کارت و مانده | فاقد `party_id`؛ نباید حساب سازمان را با حساب ذی‌نفع یکی کرد |
| `purchase_suppliers` (migration 103) | تأمین‌کننده در چرخه درخواست خرید، RFQ، سفارش، فاکتور، پرداخت، ارزیابی و قرارداد | رجیستری جدا و فاقد FK به `accounting_parties` |
| `sales_partners` (migration 102) | طرف فروش/مشتری با شناسه ملی، تلفن، ایمیل و سقف اعتبار | رجیستری جدا و فاقد FK به `accounting_parties` |
| `payment_merchants` (migration 130) | پذیرنده پرداخت با اطلاعات حقوقی، شناسه ملی/مالیاتی، IBAN، حساب تسویه، قرارداد و احراز پذیرنده | نقش تخصصی پذیرنده؛ مرجع عمومی همه طرف‌ها نیست |
| `sellers` (migration 017) | فروشنده بازارگاه با نام حقوقی/نمایشی و کمیسیون | رجیستری جدا و فاقد اتصال به party و حساب بانکی ذی‌نفع |
| `treasury_payments` و `treasury_checks` | پرداخت‌گیرنده/ذی‌نفع عمدتاً با متن `payee_name`، `beneficiary_name` و `counterparty_reference` | شناسه مرجع و رابطه قابل اتکای party/account وجود ندارد |

## پیاده‌سازی اولیه در شاخه PR #124

Migration `150_accounting_party_bank_accounts.sql` جدول حساب‌های بانکی طرف‌حساب را ایجاد کرده است؛ `accounting_bank_accounts` همچنان فقط حساب سازمان است. FK مرکب tenant+party، یکتایی IBAN در هر tenant، قالب IR+24 رقم و وضعیت احراز pending/verified/rejected تعریف شده است.

API موجود در `accounting-finance-operations.ts`:
- `GET /api/accounting-finance/operations-overview` طرف‌حساب‌ها و حساب‌های بانکی ذی‌نفعان را برمی‌گرداند و به `accounting-finance.read` محدود است.
- `POST/PATCH /api/accounting-finance/counterparties` ثبت و ویرایش سازگار با مدل ساده VamCity را انجام می‌دهد؛ ایجاد party و IBAN در یک transaction است.
- `PATCH /api/accounting-finance/parties/:id` اطلاعات عمومی party را ویرایش می‌کند.
- `GET/POST /api/accounting-finance/parties/:partyId/bank-accounts` مدیریت چند حساب بانکی برای یک party را فراهم می‌کند.
- `PATCH /api/accounting-finance/parties/:partyId/bank-accounts/:id/verification` نتیجه بررسی دستی را با actor و audit ثبت می‌کند.
- `PATCH /api/accounting-finance/parties/:partyId/bank-accounts/:id/status` وضعیت active/inactive/blocked را تغییر می‌دهد و رویداد ممیزی ثبت می‌کند.
- اعتبارسنجی API شامل نرمال‌سازی ارقام فارسی/عربی و MOD-97 است؛ DB قالب IR+24 رقم، unique tenant+IBAN و FK مرکب را enforce می‌کند. MOD-97 در تست واحد مستقل پوشش داده شده است.

UI در تب «طرف‌حساب‌ها و شبا» در همان `AccountingFinanceWorkspace` قرار گرفته است. مسیر تأیید دستی اکنون `verification_method='manual'`، actor و زمان را ثبت می‌کند. API و UI افزودن چند حساب، تغییر شبا با حفظ سابقه، فعال/غیرفعال‌سازی و مسدودسازی را دارند. خزانه/چک هنوز مصرف‌کننده حساب بانکی تأییدشده نشده‌اند.

API خرید `purchasing-supply.ts` از `purchase_suppliers` به‌عنوان مرجع FK برای RFQ، سفارش خرید، فاکتور، ارزیابی و قرارداد استفاده می‌کند. این زیرسیستم نباید با حذف یا rename جدول از کار بیفتد.

## تصمیم معماری

1. **مرجع هویت واحد:** `accounting_parties` مرجع canonical هویت طرف‌حساب در هر tenant باشد. کد و هویت اصلی شخص/شرکت فقط یک‌بار ثبت شود.
2. **نقش‌ها:** نقش‌هایی مانند مشتری، تأمین‌کننده، پذیرنده، فروشنده بازارگاه، بازاریاب، نماینده و ذی‌نفع به party متصل شوند. نقش‌های عملیاتی و وضعیت تخصصی هر زیرسیستم در همان ماژول باقی بمانند؛ party نباید به انبار تمام فیلدهای همه دامنه‌ها تبدیل شود.
3. **حساب‌های بانکی بیرونی:** رابطه‌ای مستقل و tenant-scoped برای یک party و چند حساب بانکی تعریف شده است. جدول شامل بانک، IBAN، عنوان صاحب حساب، وضعیت عملیاتی active/inactive/blocked، وضعیت احراز pending/verified/rejected، روش و یادداشت بررسی، زمان تأیید، actor تأییدکننده و زمان ایجاد/ویرایش است. یکتایی IBAN در محدوده tenant در DB enforce می‌شود.
4. **تفکیک حساب سازمان و حساب ذی‌نفع:** `accounting_bank_accounts` و `treasury_bank_accounts` برای حساب‌های خود سازمان باقی بمانند. حساب بانکی طرف‌حساب نباید به‌عنوان حساب بانکی سازمان ثبت شود.
5. **اتصال تدریجی رجیستری‌ها:** `purchase_suppliers`, `sales_partners`, `payment_merchants` و `sellers` در مرحله تطبیق داده، به party canonical وصل شوند. در ابتدا FK nullable و dual-read/validation کنترل‌شده ممکن است؛ حذف جدول یا backfill کورکورانه ممنوع است.
6. **مصرف در پرداخت:** پرداخت خزانه و چک باید به party و حساب بانکی تأییدشده ارجاع دهند. فیلدهای متنی قبلی تا زمان نگاشت، reconciliation و سازگاری backward حذف نشوند.
7. **تأیید مالکیت:** اعتبارسنجی قالب IBAN به‌تنهایی مالکیت حساب را ثابت نمی‌کند. وضعیت verified فقط با فرآیند قابل اتکا/پاسخ provider امضاشده یا بررسی مجاز انسانی ثبت شود؛ نام صاحب حساب و تاریخچه تغییرات قابل ممیزی بماند.

## مراحل باقی‌مانده

### مرحله A: تکمیل API/UI
- تست واحد MOD-97، نرمال‌سازی ارقام فارسی/عربی و رد شبا نامعتبر اضافه شده است؛ تست API رفتاری برای tenant isolation، duplicate IBAN، تغییر شبا و audit هنوز لازم است.
- مسیر provider برای احراز مالکیت حساب بانکی هنوز به انتخاب ارائه‌دهنده و قرارداد فنی نیاز دارد؛ note برای رد اجباری است.
- UI/API چندحسابی، فعال/غیرفعال/مسدودسازی و حفظ حساب‌های قبلی پیاده شده‌اند؛ خزانه هنوز مصرف‌کننده حساب verified نیست.

### مرحله B: اتصال رجیستری‌های تخصصی
- شمارش رکوردها و reconciliation بر اساس شناسه ملی/اقتصادی؛ نام مشابه به‌تنهایی مبنای merge نیست.
- اتصال مرحله‌ای `purchase_suppliers`, `sales_partners`, `payment_merchants` و `sellers` به party canonical با FKهای سازگار.
- هیچ جدول تخصصی حذف یا rename نشود و backfill بدون گزارش قبل/بعد انجام نشود.

### مرحله C: مصرف در خزانه و پرداخت
- اتصال پرداخت/چک به party و حساب بانکی verified؛ حساب pending/rejected/blocked نباید برای پرداخت قابل انتخاب باشد.
- فیلدهای متنی قدیمی تا پایان reconciliation حفظ شوند.
- IBAN validation به‌تنهایی مالکیت حساب را ثابت نمی‌کند؛ provider یا فرآیند بررسی انسانی باید قابل ممیزی باشد.

### مرحله D: backfill و cutover
- فقط پس از backup، dry-run در staging و گزارش reconciliation.
- اجرای batch قابل rollback و کنترل عدم افت رکورد/شناسه.
- cutover مرحله‌ای و حفظ مسیر بازگشت.

## مواردی که فعلاً انجام نمی‌شود

- Migration 150 و API/UI اولیه در شاخه PR #124 وجود دارند؛ CI نهایی هنوز باید موفق شود. هیچ migration روی دیتابیس تولید یا backfill انجام نشده است.
- هیچ داده‌ای از `CounterParty` یا رجیستری‌های مقصد منتقل/merge نشده است.
- هیچ شبا به‌عنوان تأییدشده تلقی نمی‌شود.
- هیچ تغییر روی دیتابیس زنده، merge یا deploy انجام نشده است.

## معیار پذیرش قبل از پیاده‌سازی

- فهرست کامل مصرف‌کنندگان هر registry و FKهای آن‌ها.
- تصمیم مکتوب درباره دامنه یکتایی IBAN (tenant-wide یا party-scoped) و چندحسابی.
- تست tenant isolation، duplicate prevention، تغییر/مسدودسازی حساب و audit.
- migration آزمایشی با حفظ تعداد و شناسه رکوردهای تخصصی.
- CI کامل روی آخرین commit و تأیید صریح قبل از اعمال تغییرات داده‌ای.


## به‌روزرسانی ادغام پذیرندگان در ۲۰۲۶-۱۰-۳۰

در ادامه مرحله B، مسیر ایجاد پذیرنده به مرجع canonical متصل شد:

- `POST /api/merchants` اکنون ایجاد party و ثبت `payment_merchants.party_id` را در یک transaction انجام می‌دهد.
- اگر در همان tenant دقیقاً یک `accounting_parties.national_id` مطابق وجود داشته باشد، همان party استفاده می‌شود.
- اگر هیچ تطبیق دقیقی وجود نداشته باشد، یک party جدید ساخته می‌شود.
- اگر بیش از یک تطبیق وجود داشته باشد، عملیات با خطای 409 متوقف می‌شود؛ سیستم حق ندارد با حدس نام یا انتخاب تصادفی دو هویت را ادغام کند.
- برای شناسه ملی، advisory transaction lock استفاده می‌شود تا دو ثبت هم‌زمان نتوانند از روی یک نبودن موقت رکورد، party تکراری بسازند.
- API فهرست و جزئیات پذیرندگان، `party_id` و عنوان طرف‌حساب canonical را برمی‌گرداند و UI پنل پذیرندگان این پیوند را نمایش می‌دهد.
- تست ساختاری برای وجود ستون `party_id`، FK مرکب tenant-safe و unique index در هر چهار رجیستری افزوده شده است. اجرای نهایی این تست وابسته به نتیجه CI آخرین commit است.

این تغییر فقط مسیر ایجاد پذیرنده‌های جدید را پوشش می‌دهد. پذیرندگان قدیمی هنوز backfill نشده‌اند و تغییر شناسه ملی رکورد موجود نیز به فرآیند reconciliation مستقل نیاز دارد. هیچ دیتابیس زنده‌ای تغییر نکرده است.
