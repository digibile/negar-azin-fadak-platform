# مرزبندی ذخیره رویدادهای لجستیک و رهگیری

## مبنای بررسی

شاخه: `feat/commerce-management-workspace`

فایل‌های بررسی‌شده:
- `apps/api/src/logistics.ts`
- `apps/api/src/migrate.ts`
- `apps/api/src/db.ts`
- `apps/api/src/notification-worker.ts`

این سند فقط آنچه از کد قابل مشاهده است ثبت می‌کند. متن migrationهای تعریف‌کننده جداول در این مرحله به‌طور کامل بازیابی و بررسی نشده‌اند؛ بنابراین درباره قیود، indexها، triggerها و جزئیات DDL این جداول ادعای قطعی نمی‌شود.

## جریان فعلی مرسوله

در `apps/api/src/logistics.ts`:

1. ایجاد مرسوله از مسیر داخلی و با کنترل tenant انجام می‌شود.
2. تغییر وضعیت از مسیر `PATCH /api/logistics/shipments/:id/status` انجام می‌شود.
3. رکورد مرسوله با `FOR UPDATE` قفل می‌شود و انتقال وضعیت با state transitionهای مجاز کنترل می‌شود.
4. در همان تراکنش، در صورت لزوم وضعیت سفارش تأمین، رزرو/مصرف/آزادسازی موجودی و رویداد موجودی به‌روزرسانی می‌شوند.
5. در پایان، یک ردیف در `logistics_delivery_events` درج می‌شود.
6. endpoint رهگیری، مرسوله و رویدادهای آن را با فیلتر tenant برمی‌گرداند.

## نقش جدول‌ها بر اساس مصرف کد

| جدول | نقش قابل مشاهده در کد | مناسب به‌عنوان inbox ورودی provider؟ |
|---|---|---|
| `logistics_delivery_events` | تاریخچه وضعیت و توضیح رویداد مرسوله | خیر؛ قرارداد پذیرش، شناسه یکتای provider و deduplication در مصرف مشاهده نشد |
| `logistics_events` | ثبت رویدادهای عملیاتی لجستیک و تغییر وضعیت | خیر؛ از کد بررسی‌شده، صف دریافت و چرخه retry/claim برای آن مشاهده نشد |
| `inventory_events` | ثبت اثرات موجودی مانند مصرف و آزادسازی رزرو | خیر؛ دفتر رویداد موجودی است، نه صف حمل |
| `platform_audit_events` | حسابرسی تغییرات سامانه | خیر؛ جایگزین inbox یا صف پردازش نیست |
| `notification_outbox` | صف پایدار تحویل اعلان‌ها | خیر؛ مصرف‌کننده و قرارداد آن اعلان‌محور است |

## شکاف‌های مشخص برای webhook شرکت حمل

در مسیر فعلی موارد زیر در کد بررسی‌شده دیده نشد:
- ذخیره خام payload ورودی همراه با شناسه یکتای رویداد provider.
- قید یکتا برای جلوگیری از پذیرش دوباره یک رویداد provider در محدوده حساب/شرکت حمل.
- وضعیت‌های مستقل دریافت، اعتبارسنجی، پردازش، شکست و تلاش مجدد رویداد ورودی.
- ثبت زمان دریافت provider و زمان رخداد provider به‌صورت جداگانه.
- سیاست صریح برای رویدادهای خارج از ترتیب و انتقال وضعیت تکراری/قدیمی.
- اعتبارسنجی امضای webhook بر اساس قرارداد واقعی provider.

این موارد به معنی اثبات نبود چنین قابلیت‌هایی در تمام مخزن نیست؛ دامنه این نتیجه فایل‌های بررسی‌شده است.

## تصمیم معماری فعلی

- `logistics_delivery_events` و `logistics_events` برای تاریخچه عملیاتی موجود حفظ شوند.
- `inventory_events` فقط برای ثبت اثر موجودی استفاده شود.
- `platform_audit_events` مرجع حسابرسی باقی بماند.
- `notification_outbox` به صف عمومی رویدادهای حمل تبدیل نشود.
- تا زمان دریافت قرارداد رسمی شرکت حمل، هیچ webhook عمومی، CSRF bypass، جدول inbox، migration یا worker جدیدی اضافه نشود.

پس از انتخاب provider، باید ابتدا قرارداد امضا، event ID، شناسه مرسوله، semantics وضعیت‌ها، retry، ترتیب رویدادها و امکان استعلام وضعیت از API رسمی آن بررسی شود. سپس طراحی ورودی provider به‌صورت idempotent و tenant-scoped انجام شود و اثر نهایی بر وضعیت مرسوله از مسیر دامنه‌ای موجود عبور کند؛ نه اینکه payload خارجی مستقیماً وضعیت سفارش یا موجودی را تغییر دهد.

## محدودیت بررسی migration

`apps/api/src/migrate.ts` مسیر migrationها را از `database/migrations` می‌خواند و فایل‌های SQL را بر اساس نام مرتب اجرا می‌کند. در این مرحله امکان فهرست‌کردن و بازیابی کامل فایل‌های آن پوشه از ابزار مخزن فراهم نشد. بنابراین DDL جداول و قیود واقعی باید در مرحله بعد با دسترسی به tree یا فایل‌های migration تأیید شود. هیچ migration یا تغییری روی دیتابیس اجرا نشده است.
