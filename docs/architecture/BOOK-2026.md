# کتاب مرجع واحد پروژه ۲۰۲۶
## پلتفرم بیزینس نگار آذین فدک ایران

**وضعیت سند:** مرجع واحد معماری، طراحی، کیفیت و چرخه ساخت.  
**مخزن اصلی:** `digibile/negar-azin-fadak-platform`  
**شاخه اصلی:** `main`

این کتاب جایگزین اسناد پراکنده معماری می‌شود. برای هر تصمیم جدید، همین سند و کد اجرایی موجود بررسی می‌شوند؛ ساخت سند موازی، پنل موازی، workflow موازی یا منبع حقیقت دوم مجاز نیست. این کتاب تضمین نمی‌کند هر قابلیت هدف از قبل پیاده‌سازی شده است؛ کامل‌بودن هر قابلیت فقط با کد، migration، تست و شواهد اجرایی تأیید می‌شود.

## ۱. ترتیب اعتبار منابع

در صورت اختلاف، ترتیب تصمیم‌گیری چنین است:

1. کد اجرایی، قرارداد API و migrationهای نسخه‌گذاری‌شده، وضعیت واقعی سامانه را مشخص می‌کنند.
2. این کتاب، قواعد معماری و معیار پذیرش تغییرات را تعیین می‌کند.
3. تست‌های خودکار و گزارش Build شواهد اجرای قراردادها هستند.
4. متن قدیمی، اسکرین‌شات، یادداشت یا طرح تأییدنشده به‌تنهایی مجوز ایجاد رفتار تازه نیست.

هر تغییر باید در محل canonical موجود اعمال شود. قبل از ساخت فایل یا endpoint جدید، جست‌وجوی مسئولیت مشابه در API، UI، migration و shared packages اجباری است.

## ۲. هویت محصول و سطح‌های آن

نام رسمی محصول «پلتفرم بیزینس نگار آذین فدک ایران» است. نام مرکز مدیریتی «مرکز مدیریت نگار آذین فدک» و نام ناوبری مرکزی «منوی مرکزی سازمان» است.

سطح‌های محصول تجربه‌های متفاوت دارند، اما هویت، نشست، مجوزها، Tenant Context و داده‌های اصلی را دوباره‌کاری نمی‌کنند:

- **Store:** فروشگاه مستقیم، کاتالوگ، سبد خرید، سفارش و پرداخت.
- **Marketplace:** کشف و مقایسه فروشندگان، فروشگاه‌ها و کالاهای فعال.
- **Seller/Acceptor:** فروشگاه، کالا، موجودی، سفارش، قرارداد، کارمزد و تسویه در محدوده مجاز.
- **Pay/Credit:** شرایط طرح، احراز هویت، درخواست، بررسی اعتبار، قرارداد، پرداخت و اقساط.
- **Corporate:** معرفی سازمان، محتوا، اخبار و کمپین‌های عمومی.
- **Management:** تنها مرکز مدیریت سازمانی برای Tenant، کاربران، نقش‌ها، مجوزها، دامنه‌ها، قالب‌ها، منوها و تنظیمات مرکزی.

هیچ سطحی نباید پایگاه کاربران، نقش‌ها، مجوزها یا APIهای موازی بسازد. نام محصول و UI نباید از اصطلاحات ممنوع در نام‌گذاری تجاری استفاده کنند.

## ۳. منوی مرکزی و ادغام ساختار قدیمی

- منبع اصلی منوی سازمانی در UI، `apps/web/app/admin/master-menu.ts` است؛ این فایل باید دقیقاً ۲۰ پنل canonical با شماره‌های ۰۱ تا ۲۰ داشته باشد.
- منوی پایگاه داده و endpoint واقعی `/api/dashboard/menu-tree` مسئول ساختار منوی ذخیره‌شده، ترتیب، وضعیت و دسترسی‌های آن هستند.
- `apps/web/app/admin/AdminSidebar.tsx` مسئول نمایش، جست‌وجو و ادغام منوی ذخیره‌شده با نگاشت canonical است.
- `apps/web/app/modules/page.tsx` dispatcher رابط ماژول‌هاست. وجود نام یک کد در فایل، به‌تنهایی اثبات اجرای واقعی آن نیست؛ مقصد باید به workspace یا مسیر عملیاتی معتبر برسد.
- کدهای قدیمی منوهای ۰۲ تا ۵۰ باید از طریق نگاشت واحد به پنل‌های جدید هدایت شوند. قابلیت مشترک یک‌بار ارائه می‌شود؛ قابلیت غیرمشترک حذف نمی‌شود و زیر مقصد canonical مناسب باقی می‌ماند.
- لینک‌های فرزند باید مقصد صریح و معتبر داشته باشند. عنوان‌های تکراریِ مستقل، مقصدهای متناقض و مسیرهای یتیم باید اصلاح شوند؛ تکرار یک قابلیت نباید با کپی‌کردن پنل حل شود.
- ساخت منوی موازی یا افزودن شماره پنل جدید خارج از قرارداد ۲۰ پنل ممنوع است. تغییرات منو باید تست پوشش legacy، مقصدها و پیمایش درختی را پاس کنند.

## ۴. نقشه حوزه‌ها و هسته‌های پیاده‌سازی

کاتالوگ حوزه‌های عملیاتی موجود، ۴۵ کد حوزه را پوشش می‌دهد. این کدها طبقه‌بندی و مسیریابی‌اند، نه ادعای تکمیل تمام عملیات تجاری.

هشت هسته اجرایی برای مالکیت کد و کاهش وابستگی‌های تکراری:

1. **Core:** سازمان، هویت، داده پایه، مشتری، تقویم، قوانین و SLA.
2. **Finance:** حسابداری، خزانه، کیف پول و دفترکل.
3. **Credit:** اعتبار، امتیازدهی، تسهیلات، قرارداد و اقساط.
4. **Commerce:** فروش، خرید، کاتالوگ، بازارگاه و سفارش.
5. **Communication:** اعلان، پیام‌رسانی، رویداد و پشتیبانی.
6. **Documents & Content:** اسناد، زونکن دیجیتال، OCR، محتوا و صفحه‌ساز.
7. **Organization:** منابع انسانی، پروژه‌ها و عملیات سازمانی.
8. **Command Platform:** گزارش، ممیزی، مستندسازی، API، زیرساخت، موبایل و کیفیت.

این دسته‌بندی مجوز ساخت سرویس یا جدول تکراری نیست. هر موجودیت باید یک مالک داده مشخص داشته باشد و سایر حوزه‌ها از API یا قرارداد مشترک به آن متصل شوند.

## ۵. معماری فنی و مرزهای داده

مسیر مرجع درخواست:

`UI → API → Domain/Service → PostgreSQL → Business Rules → Audit`

مسیر مرجع عملیات تجاری و مالی:

`Order → Payment Event → Commission → Seller Payable → Settlement → Ledger → Reconciliation → Reporting`

قواعد لازم:

- PostgreSQL پایگاه داده اصلی است؛ migrationها نسخه‌گذاری‌شده و قابل اجرای مجددِ کنترل‌شده هستند.
- عملیات تولیدی از API واقعی و داده پایدار استفاده می‌کند؛ mock، عدد ساختگی و موفقیت نمایشی در مسیر تولید ممنوع است.
- اعتبارسنجی در سرور انجام می‌شود؛ اعتبارسنجی UI جایگزین کنترل API نیست.
- هویت، permission، Tenant Scope و Entity Scope قبل از عملیات بررسی می‌شوند.
- هر تغییر حساس، actor، زمان، مرجع منبع و audit قابل پیگیری دارد.
- عملیات مالی، پرداخت، تسویه، بازگشت وجه و ارسال باید idempotent باشند و کنترل هم‌زمانی مناسب داشته باشند.
- تغییر وضعیت فقط از مسیرهای مجاز دامنه انجام می‌شود؛ درخواست نامعتبر باید خطای روشن و قابل پیگیری برگرداند.
- secrets فقط از محیط اجرا یا مخزن امن می‌آیند. هیچ کلید، رمز یا فایل `.env` در مخزن و artifact انتشار قرار نمی‌گیرد.

## ۶. Multi-tenant و هویت واحد

دامنه/Host به Tenant Context معتبر نگاشت می‌شود. هر query، mutation، cache و job باید محدوده Tenant را رعایت کند؛ مقدار Tenant دریافتی از مرورگر به‌تنهایی قابل اعتماد نیست.

هر Tenant می‌تواند دامنه، قالب، صفحه، منو، کاربران و مجوزهای محدود به محدوده خودش داشته باشد. هویت کاربر مرکزی می‌ماند و دسترسی مؤثر از نقش، permission، tenant و entity scope محاسبه می‌شود.

تست جداسازی Tenant باید تلاش برای خواندن یا تغییر داده Tenant دیگر را با پاسخ مجازِ ردشده پوشش دهد. وجود فیلد tenant در جدول به‌تنهایی اثبات isolation نیست.

## ۷. قرارداد تجربه کاربری ۲۰۲۶

- فارسی و RTL حالت پایه است؛ اجزا باید برای LTR نیز قابل تنظیم باشند.
- طراحی: Material مینیمال سازمانی، خوانا، کم‌ازدحام، زمینه روشن، خطوط ظریف و سایه محدود.
- رنگ، فاصله، تایپوگرافی و حالت‌های معنایی از design tokenهای مشترک می‌آیند؛ رنگ و CSS پراکنده برای رفع مشکل یک صفحه ممنوع است.
- فونت پایه Vazirmatn است؛ سلسله‌مراتب عنوان، توضیح، بخش، متن و metadata باید ثابت بماند.
- موبایل از عرض ۳۶۰ پیکسل پشتیبانی می‌شود. فرم‌ها نباید اسکرول افقی ناخواسته داشته باشند؛ جدول‌های پرتراکم در موبایل باید به نمایش مناسب تبدیل شوند.
- کنترل‌های لمسی حداقل ۴۴ پیکسل ارتفاع، focus قابل مشاهده، برچسب روشن و پشتیبانی از صفحه‌کلید دارند.
- هر صفحه وضعیت‌های loading، empty، error، success و retry را طراحی می‌کند. صفحه خالی یا خطای پنهان در console، تجربه کامل محسوب نمی‌شود.
- هر بخش حداکثر یک اقدام اصلی واضح دارد. حذف و اقدامات حساس تأیید و امکان بازگشت کنترل‌شده دارند.
- CSS عمومی فقط برای reset، tokenها و قواعد واقعاً سراسری است. اصلاح یک صفحه نباید با selector عمومی به صفحات نامرتبط آسیب بزند.
- کامنت فقط برای توضیح چرایی تصمیم مهم معماری یا امنیتی نگه داشته می‌شود؛ کامنت‌های قبرستانی، کد مرده و TODO بی‌مالک حذف یا به کار مشخص و قابل پیگیری تبدیل می‌شوند.

## ۸. معیار پایان هر قابلیت

قابلیت فقط وقتی «تمام» است که موارد مرتبط با دامنه را واقعاً داشته باشد:

1. migration و مدل داده سازگار؛
2. API واقعی با قرارداد روشن و خطاهای معتبر؛
3. permission، tenant/entity scope و audit؛
4. چرخه عمر و انتقال وضعیت مجاز؛
5. UI قابل استفاده با loading/error/empty/success؛
6. ایجاد، مشاهده، ویرایش و حذف/بایگانی کنترل‌شده در صورت نیاز؛
7. جست‌وجو، فیلتر، صفحه‌بندی و خروجی برای داده پرتعداد؛
8. پیوست، تاریخچه، اعلان، import/export و webhook در جایی که دامنه لازم دارد؛
9. تست واحد و API؛ تست authorization و tenant isolation برای حوزه‌های حساس؛
10. بررسی RTL، موبایل، صفحه‌کلید و مقصد تمام پیوندها.

دکمه‌ای که عملیات واقعی ندارد نباید به‌عنوان قابلیت کامل نمایش داده شود. اتصال به provider خارجی فقط با adapter، پیکربندی، timeout، retry، correlation ID و audit انجام می‌شود؛ در نبود اعتبارنامه یا قرارداد واقعی، وضعیت باید صادقانه «پیکربندی نشده» باشد.

## ۹. چرخه واقعی حوزه‌های کلیدی

### فروش و بازارگاه
`Draft → Approval/Credit Check → Confirmation → Reservation → Fulfillment → Delivery → Invoice → Payment/Settlement → Return/Refund`

هر مرحله باید قانون انتقال، actor، زمان و علت شکست یا برگشت داشته باشد.

### حسابداری و مالی
رویداد مبنا باید به سند، دفتر، تفصیلی، خزانه/بانک، تطبیق و گزارش وصل باشد. ثبت دستی سند جایگزین اتصال به رویداد مبنا نیست. سند posted باید قواعد اصلاح/برگشت روشن داشته باشد.

### اعتبار و تسهیلات
`Identity → Application → Documents/OCR → Provider Inquiry → Scoring → Decision/Approval → Contract → Disbursement → Installments → Collections → Restructuring/Closure`

تصمیم اعتبار، سقف، نرخ یا نتیجه استعلام بدون داده و منبع واقعی نمایش داده نمی‌شود. تقویم کاری و تعطیلات در محاسبه سررسید دخالت می‌کنند.

### اسناد و OCR
سند باید metadata، checksum، نسخه، مالک، سطح دسترسی، وضعیت OCR، متن استخراج‌شده، کنترل کیفیت، retention و audit داشته باشد. بازبینی انسانی زمانی لازم است که confidence پایین یا پردازش ناموفق باشد.

### ارتباطات و خروجی‌ها
ارسال از صف/outbox و adapter عبور می‌کند. خروجی حجیم job-based است: `queued → processing → completed/failed`. وضعیت تحویل، خطا و retry ثبت می‌شود؛ UI مستقیماً به SDK یک provider وابسته نمی‌شود.

## ۱۰. چرخه واحد Build، بازبینی و انتشار

تنها ورودی رسمی GitHub Actions:

`.github/workflows/deploy-sookar-main.yml`

ترتیب اجباری:

`Commit SHA → Install → Integrity/Policy Checks → API Build → Migrations → API Tests → Web Build → Clean Artifact → Human Review → Explicit Approval → Deploy/Rollback → Internal Health → Nginx → Public HTTPS`

قواعد انتشار:

1. Push به `main` مجاز به ساخت و تست و تولید artifact است؛ به‌تنهایی اجازه انتشار تولید نیست.
2. artifact باید دقیقاً از SHA مشخص ساخته شود و همان SHA پس از تأیید منتشر شود.
3. فایل‌های `.env`، secrets، `node_modules`، `.next`، cache، log، temp و backup وارد artifact نمی‌شوند.
4. استقرار تولید فقط با اجرای دستی، SHA دقیق و ورودی صریح `deploy_to_server=true` مجاز است.
5. پیش از تغییر نسخه جاری، release آماده و سلامت داخلی بررسی می‌شود؛ در شکست، rollback به نسخه قبلی انجام می‌شود.
6. سلامت API و وب، مسیر جاری release، پیکربندی Nginx و HTTPS عمومی باید از همان اجرای انتشار تأیید شوند.
7. خطای صدور SSL نباید به درخواست‌های حلقه‌ای یا مکرر منجر شود. گواهی معتبر موجود حفظ می‌شود؛ تلاش مجدد باید کنترل‌شده و قابل مشاهده باشد.
8. سبزشدن Build به معنی تأیید طراحی یا مجوز انتشار نیست. تأیید انسانی و بررسی فنی دو دروازه جدا هستند.
