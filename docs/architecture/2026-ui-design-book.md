# کتاب طراحی رابط کاربری 2026 سوکار و نگار آذین فدک

این سند مرجع واحد طراحی و تجربه کاربری پروژه است. قبل از تغییر هر صفحه، این قرارداد باید رعایت شود. طراحی قدیمی که در این کتاب تأیید نشده، مبنای توسعه صفحات جدید نیست.

## اصول محصول
- تجربه مشتری: بازارگاه سوکار، فروشگاه‌ها، کالاها، سفارش‌ها، پیگیری فروش و مسیر شفاف درخواست اعتبار/تسهیلات.
- تجربه فروشنده: مدیریت فروشگاه، کالا، موجودی، سفارش، کارمزد و تسویه در همان هویت مرکزی.
- تجربه سازمان: یک «مرکز مدیریت نگار آذین فدک» با منوی مرکزی واحد و ۲۰ پنل اصلی؛ منوهای قدیمی فقط از طریق نگاشت واحد به قابلیت‌های مشترک هدایت می‌شوند، نه با پنل‌های تکراری.
- تجربه مالی: نمایش شرایط واقعی و مستند؛ نرخ، سقف اعتبار، موجودی و وضعیت ساختگی ممنوع.
- هیچ سطح محصولی نباید هویت، نقش، مجوز، API یا جدول کاربر موازی بسازد.

## قرارداد بصری
- زبان پایه فارسی، جهت RTL؛ تمام اجزا باید در آینده قابلیت LTR داشته باشند.
- ظاهر: Material مینیمال سازمانی 2026، زمینه روشن، فضای تنفس، خطوط ظریف، سایه محدود، گوشه‌های 12 تا 20 پیکسل.
- رنگ‌های معنایی فقط از tokens مشترک: primary سرمه‌ای، accent سبزآبی، success/warning/danger؛ رنگ جدید پراکنده در صفحه ممنوع.
- فونت پایه Vazirmatn؛ سلسله‌مراتب متن ثابت: عنوان صفحه، توضیح، عنوان بخش، متن بدنه، metadata.
- دکمه اصلی برای یک اقدام مهم در هر بخش؛ اقدام ثانویه outline/quiet؛ حذف با رنگ خطر و تأیید.
- حداقل ارتفاع کنترل لمسی 44px، focus واضح، برچسب مستقل، وضعیت غیرفعال روشن، کنتراست مناسب.
- موبایل از 360px به بالا؛ نوار ناوبری جمع‌شونده، کارت‌ها تک‌ستونه، فرم‌ها بدون اسکرول افقی و جدول‌ها به کارت/لیست تبدیل شوند.
- انیمیشن کوتاه و قابل حذف با prefers-reduced-motion؛ انیمیشن صرفاً تزئینی و سنگین ممنوع.

## الگوی ثابت صفحه
1. Header: برند/مسیر، ناوبری متناسب با همان سطح، ورود یا حساب کاربری.
2. Page intro: عنوان روشن، یک توضیح کوتاه و حداکثر یک CTA اصلی.
3. Search and filters: جستجو، فیلتر قابل فهم، پاک‌کردن فیلترها.
4. Content: کارت/جدول متناسب با تراکم داده و سطح دسترسی.
5. Feedback: loading skeleton، empty state دارای اقدام بعدی، error قابل بازیابی، success قابل فهم.
6. Footer: پیوندهای مرتبط، قوانین، پشتیبانی و سطح محصول.

## قرارداد چرخه عملیات
برای هر قابلیت، متناسب با دامنه، مشاهده/جستجو، ایجاد، ویرایش، آرشیو/حذف کنترل‌شده، وضعیت و انتقال مجاز، مجوز سمت سرور، tenant scope، اعتبارسنجی، audit و تست لازم است. دکمه‌ای که عملیات واقعی انجام نمی‌دهد نباید به‌عنوان قابلیت کامل نمایش داده شود.

## مرزبندی سطح‌ها
- Store: فروشگاه مستقیم و سبد/پرداخت مشتری.
- Marketplace: کشف و مقایسه فروشندگان، فروشگاه‌ها و کالاهای فعال.
- Pay: شرایط طرح، احراز هویت، درخواست، پیگیری، قرارداد، اعتبار و اقساط.
- Seller: کالا، سفارش، موجودی، کارمزد و تسویه.
- Management: مدیریت سازمان و تنظیمات مرکزی؛ ابزارهای مدیریتی در تجربه عمومی مشتری نمایش داده نشوند.

## داده و اعتماد
- کاتالوگ عمومی فقط از API واقعی دریافت می‌شود. نمونه‌های ساختگی، اعداد ساختگی و وعده اعتبار قطعی ممنوع.
- قیمت باید با واحد ارز نمایش داده شود و قیمت نهایی/اعتباری تا زمان quote معتبر قطعی تلقی نشود.
- پیام خطا باید اقدام بعدی مشخص داشته باشد؛ خطای API در صفحه خالی یا console پنهان نشود.
- وضعیت خالی با پیام روشن نشان داده شود و هرگز به‌عنوان موفقیت یا داده موجود جا زده نشود.

## قانون ضد قبرستان
- یک workflow رسمی، یک منوی مرکزی، یک منبع token و یک نگاشت legacy به canonical.
- پیش از ساخت فایل جدید، اجزای مشترک و مسیر موجود بررسی شود.
- فایل موازی با همان مسئولیت ساخته نشود؛ تغییر باید در محل canonical انجام شود.
- کامنت فقط برای چرایی تصمیم معماری است.
- فایل‌های محیطی، secrets، cache، خروجی build و backup وارد artifact انتشار نمی‌شوند.

## پذیرش صفحه
- build TypeScript/Next موفق.
- loading/error/empty/success قابل مشاهده.
- موبایل، RTL و keyboard بررسی شوند.
- تمام پیوندها مقصد معتبر داشته باشند.
- داده از API واقعی باشد و عملیات حساس به API مجاز سمت سرور واگذار شود.
- تا پیش از تأیید انسانی، artifact ساخته و بررسی می‌شود؛ deploy تولید فقط با تأیید صریح انجام می‌شود.
