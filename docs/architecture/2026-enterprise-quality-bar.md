# استاندارد اجرایی کیفیت سازمانی 2026

این سند Definition of Done مشترک برای همه قابلیت‌های پلتفرم است. یک صفحه زیبا بدون چرخه عملیاتی کامل، قابلیت تکمیل‌شده محسوب نمی‌شود.

## 1. قرارداد مشترک هر قابلیت

- ایجاد، مشاهده، ویرایش، حذف یا بایگانی کنترل‌شده
- وضعیت و چرخه عمر صریح؛ تغییر وضعیت فقط از مسیرهای مجاز
- نقش، مالک، مسئول و محدوده سازمانی
- اعتبارسنجی سمت کاربر و سمت سرور
- تاریخچه تغییرات و Audit Trail
- توضیح متنی و در موارد مناسب توضیح صوتی
- فایل و پیوست، مشاهده، دانلود و ارتباط با موجودیت اصلی
- جستجو، فیلتر، مرتب‌سازی، صفحه‌بندی و saved views در موارد پرتعداد
- خروجی CSV/XLSX/PDF متناسب با داده
- ارسال ایمیل/SMS/Push/پیام‌رسان از صف ارتباطی، نه اتصال مستقیم صفحه به provider
- اعلان رویدادها و تاریخچه تحویل
- import در جایی که حجم عملیات انسانی زیاد است
- API و Webhook برای موجودیت‌های یکپارچه‌شونده
- idempotency برای عملیات مالی، پرداخت، تسویه و ارسال
- optimistic/concurrency control برای رکوردهای حساس
- دسترسی حداقلی و tenant isolation
- empty/loading/error/success/retry state کامل
- keyboard, mobile, RTL/LTR و accessibility

## 2. تیکت و پشتیبانی

چرخه پیش‌فرض: جدید → باز → در حال بررسی → در انتظار مشتری / در انتظار واحد داخلی / معلق → حل‌شده → بسته‌شده.

مسیرهای کنترل‌شده بازگشایی‌شده و لغوشده نیز وجود دارند.

هر تیکت باید علاوه بر وضعیت، اولویت، اثر، فوریت، دسته‌بندی، کانال، درخواست‌کننده، مسئول، SLA پاسخ و SLA حل، زمان اولین پاسخ، زمان حل و کد علت حل را نگهداری کند.

این چرخه با الگوهای رایج مدیریت incident/service desk هم‌راستا است، اما برای سازمان قابل پیکربندی می‌ماند.

## 3. اسناد و پرونده دیجیتال

اسناد فقط فایل نیستند. برای هر سند metadata و context، checksum، creator/uploader، timestamp، ارتباط با فاکتور/پرداخت/سفارش/قرارداد/پرونده/زونکن، نسخه و تاریخچه، وضعیت OCR، متن استخراج‌شده، وضعیت کنترل کیفیت، سطح دسترسی، نگهداری/آرشیو/امحای کنترل‌شده و Audit باید قابل مدیریت باشد.

اصل طراحی بر قابلیت‌های authenticity, reliability, integrity و usability و اهمیت metadata در مدیریت records بنا شده است.

## 4. ثبت بدون تایپ

- camera capture در موبایل
- file picker و scanner workflow در سیستم
- تبدیل client-side تصاویر به WebP با کاهش منطقی حجم
- voice input برای فیلدهای متنی
- voice note برای توضیحات
- OCR job queue
- human review فقط زمانی که confidence پایین یا provider خطا دارد
- autocomplete و انتخاب از داده‌های شناخته‌شده
- جلوگیری از ورود دوباره اطلاعات موجود

هدف حذف تایپ تکراری است، نه افزودن یک دکمه میکروفن تزئینی.

## 5. حسابداری و مالی

هر رویداد مالی باید به زنجیره واقعی متصل باشد: عملیات تجاری → سند مبنا → فاکتور/دریافت/پرداخت → سند حسابداری → دفتر/تفصیلی → خزانه/بانک → تطبیق → گزارش.

ثبت دستی سند جایگزین رویداد مبنا نیست. سند حسابداری باید source reference، actor، زمان، وضعیت posting و audit داشته باشد.

## 6. فروش و خرید

فروش و خرید باید چرخه واقعی داشته باشند: draft → approval/credit checks در صورت نیاز → confirmation → reservation → fulfillment → delivery → invoice → payment/settlement → return/refund و accounting linkage.

هر مرحله باید قواعد انتقال و علت شکست یا برگشت را ثبت کند.

## 7. اعتبار، تسهیلات و بیمه کالا

در اعتبار و تسهیلات: احراز هویت، پرونده، دریافت مدارک، OCR، اعتبارسنجی، استعلام provider، scoring، تصمیم، کمیته/تأیید در صورت policy، قرارداد، پرداخت، اقساط، وصول، معوق، بازسازی و مختومه‌سازی.

استعلام‌ها باید provider adapter، request/response audit، correlation id، timeout، retry و وضعیت مشخص داشته باشند.

برای بیمه کالا نیز چرخه باید شامل انتخاب پوشش، استعلام، محاسبه حق بیمه، صدور، وضعیت بیمه‌نامه، الحاقیه/لغو و پیگیری خسارت باشد.

## 8. خروجی و ارتباطات

هیچ صفحه پرتعداد نباید فقط جدول و دکمه دانلود داشته باشد. خروجی‌ها job-based می‌شوند: queued → processing → completed/failed.

نتیجه دارای نام فایل، نوع، فیلترهای استفاده‌شده، کاربر، زمان و audit است.

ارتباطات نیز از outbox عبور می‌کنند تا UI به provider وابسته نباشد.

## 9. استاندارد UI

- Persian RTL اول، LTR-ready
- WCAG 2.2 AA target
- responsive واقعی، نه فقط کوچک‌کردن جدول
- focus state، keyboard access و status announcements
- فرم‌های کوتاه و کم‌خطا
- جلوگیری از redundant entry
- actionهای مهم واضح و قابل بازگشت
- data-dense ولی خوانا
- empty/error/loading states طراحی‌شده
- طراحی هر سطح با Design System مشترک
- CSS ماژولار، بدون فایل‌های عظیم و انباشته

## 10. Definition of Done

قابلیت فقط زمانی تمام است که:
1. DB migration دارد.
2. API واقعی دارد.
3. permission دارد.
4. tenant isolation دارد.
5. lifecycle دارد.
6. UI کامل دارد.
7. create/edit/view/delete یا archive متناسب با domain دارد.
8. attachments و comments در صورت نیاز دارد.
9. audit دارد.
10. notification/communication در صورت نیاز دارد.
11. export/import متناسب با domain دارد.
12. mobile و accessibility بررسی شده است.
13. build/test/verification سبز است.
14. مستندات «چرا این معماری» به‌روز است.

این معیار برای همه منوهای 1 تا 50 اعمال می‌شود؛ تعداد صفحه معیار کیفیت نیست.
